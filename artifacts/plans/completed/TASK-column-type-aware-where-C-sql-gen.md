# Task: Type-Aware SQL WHERE Generation + Tests

## Problem Statement

Part C of the "Column-Type-Aware SQL WHERE" feature. Depends on Part B (Catalog Type Propagation) which adds optional `colType?: ColumnType` to `PhysicalColEntry` and `BandColEntry` in the colMap.

The current `buildWhere` in `sql-where.ts` uses `isNumericCalc()` (lines 53-56) as its only type hint — this only triggers for calculated columns with `kind: 'calc' && mode: 'math'`, missing physical columns with numeric data from spreadsheets. Comparison operators (`>`, `<`, `>=`, `<=`) unconditionally use `CAST(col AS REAL)` (lines 94-97), which destroys leading zeros in text columns (zip codes like '02134' become 2134). The `ColStateEntry` interface (lines 26-30) and `_colState` parameter (line 198) are dead code from the Preact conversion — no caller passes `_colState`.

This plan replaces the `numericHint` mechanism with `getColumnType()`, which reads `ColumnType` from colMap entries (propagated by Part B) or derives it from calc column mode. All SQL generation becomes type-aware: number/boolean columns use `CAST(ref AS REAL)`, string/date columns use `CAST(ref AS TEXT)`, and comparison operators default to TEXT (fixing the leading-zero bug). The `buildWhere` API is cleaned to exactly 2 params as the design doc requires.

**Prerequisite:** TASK-column-type-aware-where-B (Catalog Type Propagation) must be completed first — Part C reads `colType` from colMap entries that Part B creates.

## Completion Criteria
- `isNumericCalc()` and `ColStateEntry` are fully removed from `sql-where.ts` and `index.ts`
- `getColumnType()` correctly derives ColumnType from colMap entries (physical/band colType, calc mode derivation, _rowno special case, default fallback)
