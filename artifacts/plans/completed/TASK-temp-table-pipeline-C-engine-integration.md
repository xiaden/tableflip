# Task: Pipeline Engine & Integration

## Problem Statement

The temp-table pipeline architecture (DD-temp-table-pipeline) replaces the current monolithic SQL-composed query approach with sequential stage functions that each create a temp table. Parts A and B provide the data model (new fields on ReportSpec: `includeSourceColumn`, `sourceColumnName`, `stackAliases`) and six stage functions (`executeBaseStage`, `executeLookupStage`, `executeCalcStage`, `executeFilterStage`, `executeSortStage`, `executeAggregationStage`). This plan (Part C) wires those stage functions into a working pipeline: it creates the `PipelineEngine` class that orchestrates stage execution, refactors `buildQueryPlan()` to return stage configs instead of composed SQL, updates `runReport()` to use the pipeline engine, simplifies the preview builder, migrates validation to read temp table schemas, and integrates detail bands with the pipeline.

**Prerequisite:** TASK-temp-table-pipeline-A-data-model (Part A) and TASK-temp-table-pipeline-B-stage-functions (Part B) must be executed first.

## Completion Criteria

- `SRC/preact/report/pipeline-engine.ts` exists with `PipelineEngine` class, `PipelineState` interface, module-level singleton, and exported `getPipelineState()`/`getPipelineEngine()` accessor functions
- `PipelineEngine.execute()` calls `buildQueryPlan()` for catalog/config building (or accepts pre-built configs), then orchestrates the six stage functions from Part B, tracking temp table state via `PipelineState`
- `PipelineEngine.invalidateFromStage()` drops downstream temp tables and updates `validUpToStage`
- `PipelineEngine.cleanup()` drops all `_pipeline_*` temp tables and resets state
- `buildQueryPlan()` returns `QueryPlanConfigs` — no `sql`, `params`, or `cols` fields; adds `sourceCatalog` field; all catalog-building logic preserved
- `runReport()` uses `PipelineEngine.execute()` instead of `buildQueryPlan()` + mode dispatch; no `switch(aggMode)` remains; mode-specific runner functions (`runDetailMode`, `runTotalsMode`, `runSubtotalsMode`, `runGroupedMode`) are deleted
- `runDetailBandsMode()` reads parent rows from `pipelineState.tempTableNames[4]` via pipeline state instead of executing `plan.sql`; uses `configs.colMap` and `configs.sourceCatalog` instead of rebuilding catalogs
- `preview-builder.ts` is simplified to SELECT from pipeline temp tables (≤100 lines, down from 365); `buildPreview()` signature unchanged
- `validation.ts` `deriveValidation()` reads temp table schemas via `PRAGMA table_info()` when pipeline state is available; falls back to colMap-based validation when temp tables don't exist
- `invalidateValidation()` is called after pipeline temp table creation/destruction (constraint #9)
- All SQL identifiers use `quoteId()` — no string concatenation of identifiers
- All existing tests updated for `QueryPlanConfigs` return type — zero references to `plan.sql`, `plan.params`, or `plan.cols` in test files
- `npm run typecheck` passes with zero errors
- `npm run lint` passes with zero warnings
- `npm test` passes with all tests green
